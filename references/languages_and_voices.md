# Languages, male/female voices and translations (v2)

## 1. How a line is picked at call time

For every `<say>`, `<filler>` and global `filler`, the runtime picks one `<text>`:

1. the call's current language (the language the turn is spoken in), exact code first (`hi-IN`), then base
   language (`hi`);
2. else the bot's primary language (`bot_language`);
3. else the first `<text>`.

Inside the chosen `<text>`, a `<male>`/`<female>` pair is resolved by the system variable `agent_gender`, which
genvoice-call-message sets at call start from the bot's active voice persona (`Male`/`Female`). Anything other
than `Male` (missing, empty) gets the **female** line.

Consequences:
- Write a `<text>` for **every** bot language in every `<say>`/`<filler>`. Only the primary is enforced; a missing
  one silently speaks the primary-language line to a caller in another language.
- A `<say>` costs no model call when everything shown in the scenario is `<say>` lines and no exit is shown
  (see `runtime_and_latency.md`).
- The same bot can be re-voiced (male ↔ female persona) without editing the config, as long as gendered lines
  are written as pairs.

## 2. Male/female pairs

**Write every `<text>` as a `<male>` + `<female>` pair, in every language, in every `<say>`, `<filler>` and global
`filler`.** That is what the editor's Translate produces; a `<say>` mixing paired and plain `<text>` loses the
plain ones when the editor re-saves it, and plain-only lines are flagged as untranslated. Runtime cost is zero:
only the one picked line is rendered. (Both voices do count toward the 5000-char scenario text limit.)

The two versions **differ** only where the language marks the **speaker's** gender: first-person verb endings,
participles, adjectives and pronouns that refer to the agent. Elsewhere they are identical. The caller's gender
("sir", "madam") never matters.

| Marks speaker gender in first person | Usually not |
|---|---|
| Hindi, Urdu, Marathi, Gujarati, Punjabi, Rajasthani/Haryanvi forms, Arabic (participles/adjectives: متأسف/متأسفة) | English, Tamil, Telugu, Kannada, Malayalam, Bengali, Odia, Assamese, Japanese (polite register) |

- Hindi: `मैं चेक कर रही हूँ` / `मैं चेक कर रहा हूँ`; `मैं कॉल करूँगी` / `करूँगा`; `मैं समझ गई` / `गया`.
- Marathi: `मी तपासते` / `मी तपासतो`; `मी सांगितलं` is neutral.
- Gujarati: `હું તપાસ કરું છું` is neutral; `હું આવી` / `હું આવ્યો` differs.
- Lines with no speaker-gender word get identical male and female text: `एक मिनट होल्ड कीजिए`.

Check every first-person verb and adjective in each language before copying one voice into the other.

```xml
<say>
  <text lang="en-IN">
    <male>I am checking your payment details now.</male>
    <female>I am checking your payment details now.</female>
  </text>
  <text lang="hi-IN">
    <male>मैं अभी आपकी पेमेंट डिटेल्स चेक कर रहा हूँ।</male>
    <female>मैं अभी आपकी पेमेंट डिटेल्स चेक कर रही हूँ।</female>
  </text>
</say>
```

### Free-form replies (not `<say>`)

Most of what the agent says is generated by the model, which also needs the right gender forms. Put this in a
global prompt section (KV-safe: it reaches the head as `[agent_gender]`, the value comes per turn):

```
Your voice is {{agent_gender}}. In Hindi, Marathi, Gujarati and Punjabi use first-person verb and adjective forms
that match a {{agent_gender}} speaker (female: रही हूँ, गई, करूँगी; male: रहा हूँ, गया, करूँगा).
```

Do not hard-code a gendered persona name or gendered verbs in `persona` when the voice can change; use
`{{agent_name}}` (system, from the voice persona).

## 3. Writing the lines (platform translation house style)

The editor's Translate button calls `POST /genbots/v3/{botId}/translations/generate?environment=development`
(`{sourceText, targetLanguages}` → `{translations: {lang: {female, male}}, errors}`; 10 requests/min, development
only for org bots, nothing saved). Its prompt defines the style; write lines the same way so they read like the
rest of the platform's bots:

1. **Spoken, not written.** How a friendly phone agent in that country talks: short sentences, everyday words,
   meaning over word-for-word, similar length and politeness to the source. No Sanskritized Hindi or literary
   Tamil.
2. **Everyday English loanwords stay English but in the native script**: `कन्फर्म`, `पेमेंट`, `लोन`, `अकाउंट`,
   `डिटेल्स`, `नंबर`, `कॉल`. Never leave Latin spelling inside a sentence in another script.
3. **Names and abbreviations stay exactly as in the source** (Latin is fine): bank, product, scheme, plan names,
   `RBI`, `OTP`, `EMI`. Ordinary words around them are translated.
4. **Numbers stay as written.** `{{name}}` placeholders are copied unchanged into every language.
5. **Plain text only.** Letters, digits, spaces and `. , ? ! ' - : ; … । ॥ ؟ ، ۔`. Write symbols as words
   (`rupees`/`रुपये`, `percent`/`प्रतिशत`, `and`/`और`). No quotes, brackets, emojis, markdown, `₹`, `%`, `&`, `/`.
6. **One `<text>` per language holds the whole line**, all its sentences. Never one `<text>` per sentence.

Example (en-IN source → hi-IN): "Your payment is due tomorrow. Please confirm if you can pay on time." →
`आपका पेमेंट कल तक करना है। क्या आप टाइम पर कर पाएँगे?`

Fillers are plain text (no `{{name}}`): keep them short (2-6 words) and generic so they fit any branch:
`One moment.` / `एक सेकंड।`, `Sure, let me check.` / `जी, मैं चेक करती हूँ।` (female) / `करता हूँ` (male).
A filler must not end the thought or ask a question: the next scenario continues right after it.

## 4. Language rules for generated replies

Put the bot's language policy in one global prompt section (e.g. `language_rules`), not in scenarios. Typical
content: reply in the caller's language, one language per reply, mirror switches, keep brand names in Latin, say
numbers the way that language's speakers say them, read amounts in words if the TTS mispronounces digits. If the
bot supports a fixed set of languages, name them (`English and Hindi only; if the caller speaks another language,
continue in Hindi`).
